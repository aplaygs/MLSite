У каждой вещи своя полка

8 мин

Зачем: проект, где всё свалено в одну папку, нельзя ни продолжить, ни показать. Порядок в папках — первое, что видно по ссылке на GitHub.

Почти все ML-проекты раскладывают одинаково. Выучишь один раз — и в любом чужом проекте будешь знать, где что лежит.

oulad-risk/ ├── README.md # витрина: что за проект и как запустить ├── requirements.txt # список библиотек (урок 1.3) ├── .gitignore # что не класть в git (шаг 3) ├── data/raw/ # данные как скачали — руками не трогаем ├── data/processed/ # данные после обработки кодом ├── notebooks/ # черновики и исследования: 01_eda.ipynb ├── src/oulad_risk/ # код проекта: загрузка, признаки, обучение ├── tests/ # проверки кода └── models/ # обученные модели

Главное правило: ноутбук — для исследований, код — в src/. Если функция понадобилась во втором ноутбуке, её переносят в src и импортируют.

Так это называютструктура проекта; папка с кодом и файлом __init__.py внутри — пакет (package), его можно импортировать: from oulad_risk import load.

data/raw — не трогаем, notebooks — черновики, src — код, models — результаты.

Подробнее: имена файлов, пакет и что ещё бывает в проекте · 3 минуты
  • Ноутбуки нумеруют: 01_eda.ipynb, 02_baseline.ipynb, 03_features.ipynb — по номеру видно порядок работы. Имена — латиницей, маленькими буквами, через подчёркивание, без пробелов.
  • Папка-пакет. src/oulad_risk/ с файлом __init__.py внутри — это пакет. Чтобы импортировать его из ноутбука в notebooks/, проект ставят в окружение командой pip install -e . (нужен файл pyproject.toml — сделаем, когда кода станет больше). Пока можно так: в первой ячейке ноутбука import sys; sys.path.append("../src").
  • Ещё папки, которые встретишь в чужих проектах: configs/ — настройки обучения (yaml), reports/ — графики и таблицы для README, scripts/ — запуск из терминала.
  • Почему data/raw не трогают: если что-то пошло не так, processed всегда можно пересоздать кодом из raw. Правишь raw руками — теряешь возможность повторить результат.

README — витрина проекта

7 мин

Зачем: на отборе на проект смотрят 1–2 минуты. Почти всё это время уходит на первый экран README.

README — первое, что показывает GitHub. Хороший README отвечает на пять вопросов, сверху вниз:

  • Что за задача — одной фразой, без «проект по машинному обучению».
  • Какой результат — число и с чем сравнивал: «лучше, чем модель, которая всем отвечает одно и то же».
  • Какие данные — откуда скачать (сами данные в git не кладут).
  • Как запустить — 3–5 команд, которые работают в чистой папке.
  • Что где лежит — коротко про папки.

Первая строка README — задача и результат, а не «учебный проект».

.gitignore — чего git не должен видеть

8 мин

Зачем: данные весят гигабайты, окружение своё на каждом компьютере, пароли — секрет. Всё это в git попасть не должно.

.gitignore — обычный текстовый файл в корне проекта. Каждая строка — что git должен не замечать. Например, data/ — всю папку целиком, *.csv — все файлы с таким концом, .env — один файл.

Обычный набор для ML-проекта: .venv/, data/, models/, .env, __pycache__/, .ipynb_checkpoints/.

Ловушка

.gitignore работает только для файлов, которые ещё не в git. Если data уже закоммитили, сначала убери её из отслеживания: git rm -r --cached data, потом коммит. Поэтому .gitignore делают первым же коммитом.

Подробнее: как читать правила .gitignore · 3 минуты
  • # текст — комментарий. *.csv — все csv в любой папке. data/ — папка data где угодно. /data/ — только в корне проекта.
  • !data/.gitkeep — восклицательный знак делает исключение: всю data прячем, а пустой файл-заглушку оставляем, чтобы папка была в репозитории.
  • **/__pycache__/ — две звёздочки: на любой глубине.
  • На Mac добавь .DS_Store — служебный файл Finder, он появляется в каждой папке.
  • Не понимаешь, почему файл не виден git? git check-ignore -v путь покажет, какое правило его прячет.

Пароли — в .env, а не в коде

7 мин

Зачем: ключ от API, случайно попавший на GitHub, находят боты за минуты. Это реальная история, и на код-ревью за такое сразу заворачивают.

Пароли и ключи живут в файле .env рядом с проектом. Он в .gitignore, то есть только на твоём компьютере. Код читает ключ из окружения, а не держит его в тексте.

Чтобы коллега знал, что задать у себя, в git кладут .env.example — те же имена, но без значений.

# .env — только у тебя, в .gitignore
KAGGLE_KEY=a1b2c3d4

# .env.example — в git, без значений
KAGGLE_KEY=

# в коде
import os
from dotenv import load_dotenv   # pip install python-dotenv
load_dotenv()                    # читает .env в переменные окружения
key = os.environ["KAGGLE_KEY"]   # нет ключа — сразу понятная ошибка

Пароль в коде = пароль у всех. Ключ утёк — первым делом отзови его, потом чисти историю.

Подробнее: python-dotenv и что делать, если ключ утёк · 2 минуты
  • Библиотека ставится как pip install python-dotenv, а импортируется как dotenv — имена разные, это нормально.
  • os.environ["KEY"] — нет ключа → сразу ошибка KeyError (хорошо: сразу видно). os.environ.get("KEY", "") — нет ключа → пустая строка, ошибка вылезет позже и непонятно где.
  • GitHub сам сканирует публичные репозитории на ключи и иногда предупреждает — но боты злоумышленников делают это быстрее.
  • Порядок при утечке: 1) отозвать ключ в сервисе, 2) выпустить новый, 3) убрать файл из истории (git filter-repo — инструмент для этого), 4) добавить .env в .gitignore.

Версии: чтобы через полгода всё запустилось

6 мин

Зачем: «у меня работало» — самая частая беда учебных проектов. Причина почти всегда в том, что поставилась другая версия библиотеки.

Номер версии читается так: 2.2.3 — это большая.средняя.маленькая. Маленькая — исправили ошибки. Средняя — добавили новое, старое работает. Большая — могли что-то сломать.

  • pandas==2.2.3 — ровно эта версия. Так пишут в проекте: воспроизводится один в один.
  • pandas>=2.2 — «эта или новее». Через полгода приедет 3.0, и код может сломаться.
  • Версию самого Python тоже пишут в README: «Python 3.12».
Так это называютфиксация версий (pinning); схема «большая.средняя.маленькая» — SemVer, по-английски MAJOR.MINOR.PATCH.
Подробнее: pip freeze, ~= и проверка «с нуля» · 3 минуты
  • pip freeze > requirements.txt записывает все пакеты окружения с точными версиями, включая зависимости зависимостей. Быстро, но список длинный. Многие пишут руками только главные библиотеки с == — тоже нормально.
  • pandas~=2.2.3 — «совместимая версия»: 2.2.3, 2.2.4 и дальше, но не 2.3. Компромисс между точностью и исправлениями ошибок.
  • Лучшая проверка: новая папка → git clone → новый venv → pip install -r requirements.txt → запуск по README. Запустилось — проект воспроизводим.
  • Версию Python пишут в README («Python 3.12») — у разных версий бывают разные пакеты.

Коммиты, по которым понятна история

7 мин

Зачем: история из «fix», «правки», «ещё правки» никому ничего не говорит. По подписям коммитов на отборе видно, работал ли человек в команде.

Договорённость, которой пользуются многие команды: тип: что сделал, по-английски, коротко, в повелительном наклонении.

feat: add data loaderновая возможность
fix: handle empty csvисправление ошибки
docs: describe datasetдокументация, README
refactor: split train.pyпереписал без изменения поведения
test: check no leakageтесты
chore: add gitignoreслужебное: настройки, зависимости
Лаборатория · проверь подпись коммита
    Так это называютConventional Commits — эта договорённость; feat(data): … — в скобках можно указать часть проекта.

    Один коммит — одно изменение. Подпись: тип: что сделал.

    Подробнее: длинное описание, «!» и как поправить последний коммит · 2 минуты
    • Подпись — в повелительном наклонении: add loader, а не added loader. Читается как «этот коммит: add loader».
    • Нужны подробности — пустая строка после подписи и дальше текст: git commit без -m откроет редактор.
    • feat!: change data format — восклицательный знак: изменение ломает старое поведение.
    • Опечатался в подписи и ещё не сделал push — git commit --amend -m "fix: правильная подпись". После push историю лучше не переписывать.
    Частые ошибки
    • data/ и .venv в репозитории.gitignore — первым коммитомПотом придётся вычищать историю.
    • API_KEY = "a1b2c3" в train.pyos.environ["API_KEY"] + .envПароль в коде — пароль у всех.
    • одна и та же функция в трёх ноутбукахфункция в src/, ноутбуки её импортируют
    • pandas (без версии)pandas==2.2.3Через полгода установится другая версия.
    • git commit -m "правки"git commit -m "fix: handle empty csv"

    Работа · 20 минут

    Скелет проекта на GitHub

    1. Создай папку ~/projects/oulad-risk со структурой из шага 1 (пустые папки — с файлом .gitkeep, иначе git их не увидит).
    2. Первым коммитом — .gitignore из шага 3.
    3. README с разделами: задача, данные, как запустить (результат пока пустой). Данные — OULAD, скачай в data/raw.
    4. .env.example и requirements.txt с версиями через ==.
    5. 3–4 коммита с подписями по шагу 6, потом push на GitHub.

    Готово, когда на GitHub видны README, .gitignore и папка src, а папок data и .venv там нет.

    Команды для начала
    mkdir -p ~/projects/oulad-risk/{data/raw,data/processed,notebooks,src/oulad_risk,tests,models}
cd ~/projects/oulad-risk
touch src/oulad_risk/__init__.py tests/.gitkeep notebooks/.gitkeep
printf ".venv/\ndata/\nmodels/\n.env\n__pycache__/\n.ipynb_checkpoints/\n" > .gitignore
git init && git add .gitignore && git commit -m "chore: add gitignore"

    {data/raw,notebooks} — фигурные скобки создают несколько папок одной командой. printf с \n пишет несколько строк в файл.

    На собеседовании

    Так спрашивают на отборах на стажировку. Сначала ответь вслух сам, потом открой ответ.

    СобеседованиеКак ты организуешь репозиторий ML-проекта?

    Разделяю данные, исследования и код: data/raw (не трогаю руками) и data/processed, notebooks для экспериментов, src с пакетом для повторно используемого кода, tests и models. В корне README с задачей, результатом и инструкцией запуска, requirements.txt с точными версиями и .gitignore, чтобы данные, окружение и секреты не попали в git.

    СобеседованиеКак другой человек повторит твой результат?

    Клонирует репозиторий, создаёт venv и ставит пакеты из requirements.txt с зафиксированными версиями, скачивает данные по ссылке из README и запускает команды из раздела «Как запустить». Случайность фиксирую через random_state, поэтому цифры совпадут.

    СобеседованиеТы закоммитил ключ API в публичный репозиторий. Что делаешь?

    Сначала отзываю ключ и выпускаю новый — старый уже мог быть скопирован. Потом убираю файл из истории git, а ключ переношу в .env, который в .gitignore; в репозиторий кладу .env.example без значений.

    1. Папки: data/raw (не трогаем), data/processed, notebooks (черновики), src (код), tests, models.
    2. README: задача одной фразой → результат с числом → данные → как запустить → что где.
    3. .gitignore: .venv/, data/, models/, .env, __pycache__/ — первым же коммитом.
    4. Пароли — в .env (в .gitignore), в git — .env.example без значений, в коде — os.environ.
    5. Версии: == в проекте; большая.средняя.маленькая; версия Python — в README.
    6. Коммиты: тип: что сделал (feat, fix, docs, refactor, test, chore). Один коммит — одно изменение.
