Структура проекта: src/, tests/, configs/

У каждой вещи в проекте своё место: код — в src/, проверки — в tests/, настройки — в configs/, исследования — в notebooks/, данные и модели — рядом, но не в git. Так проект понятен чужому человеку и запускается одной командой.

  • Почему не всё в одном ноутбуке: ноутбук нельзя импортировать, тестировать и запускать на сервере по расписанию. Ноутбук — для исследования и графиков, всё повторяемое переезжает в функции в src/.
  • Одна ответственность на модуль: data.py — загрузка и очистка, features.py — признаки, train.py — обучение, evaluate.py — метрики. Модуль на 1000 строк — сигнал разбить.
  • Конфиги вместо чисел в коде: пути, гиперпараметры, список признаков — в configs/*.yaml или .json. Новый эксперимент — новый конфиг, а не правка кода.
  • Данные по слоям: data/raw — как скачали, никогда не менять руками; data/processed — то, что получилось скриптом. Любой файл в processed можно пересоздать из raw.
  • pyproject.toml — паспорт проекта: имя, версия Python, зависимости, настройки инструментов (линтер, тесты). Минимальный уже позволяет pip install -e ..
Ловушка импортов

«В ноутбуке импорт работает, а скрипт падает с ModuleNotFoundError» — почти всегда разные текущие папки и sys.path. Не лечи это строчкой sys.path.append("..") в каждом файле: установи пакет через pip install -e . или запускай модулем через python -m из корня.

.gitignore для данных, моделей и секретов

Зачем нужен .gitignore — в уроке 1.3. Здесь — как он на самом деле читает правила: что значит слэш в начале и в конце, звёздочки, восклицательный знак и почему исключение иногда не срабатывает.

Лаборатория · проверка .gitignore

Правь правила слева — справа сразу видно, какие файлы попадут в git (зелёным — по какому правилу оставлен), а какие нет (зачёркнуто — каким правилом скрыт). Работает как git check-ignore -v для простых случаев.

ПравилоЧто значит
*.csvвсе .csv в любой папке
data/папка data где угодно (слэш в конце — только папки)
/data/только data в корне репозитория
models/**/*.pklpkl на любой глубине внутри models
!data/README.mdисключение: этот файл оставить
# комментарийстрока не правило
Почему исключение не работает

Если скрыта папка целиком (data/), git в неё даже не заглядывает, и !data/README.md ничего не вернёт. Нужно скрыть содержимое, а не папку: data/*, а потом !data/README.md. Проверь это кнопкой «Ловушка с исключением». Отладка в настоящем репозитории: git check-ignore -v путь — покажет, какое правило сработало.

  • Уже закоммиченный файл .gitignore не скроет: git rm --cached файл, потом коммит.
  • Секрет попал в историю — считай его утёкшим: сначала отозвать ключ у сервиса, потом чистить историю. Удаление файла новым коммитом не помогает — старый коммит всё помнит.
  • Общий gitignore для мусора системы и редактора (.DS_Store, .idea/): git config --global core.excludesfile ~/.gitignore_global.
  • Данные и модели всё-таки хочется версионировать — для этого DVC или Git LFS, а не git напрямую (неделя MLOps).

Первым делом отзываю токен у сервиса и выпускаю новый — после пуша его могли скопировать за секунды, боты сканируют GitHub. Секреты в .env, а не в коде

Пароли, токены и ключи API живут в переменных окружения. Локально их удобно хранить в файле .env, который никогда не попадает в git. В репозиторий кладут .env.example — те же имена без значений.

# .env — в .gitignore, только на твоём компьютере
OPENAI_API_KEY=sk-...
DB_URL=postgresql://user:pass@localhost/oulad

# .env.example — в git: какие переменные нужны
OPENAI_API_KEY=
DB_URL=

# код читает из окружения; python-dotenv подгружает .env при старте
import os
from dotenv import load_dotenv
load_dotenv()                                   # ищет .env и кладёт значения в os.environ
key = os.environ["OPENAI_API_KEY"]              # нет переменной — KeyError: падаем сразу и понятно
debug = os.getenv("DEBUG", "0") == "1"           # необязательная — со значением по умолчанию
  • Что считается секретом: всё, что даёт доступ: ключи API, пароли БД, токены ботов, приватные ключи SSH, строки подключения. Не секрет — пути, гиперпараметры, имена моделей: это конфиг.
  • Откуда секреты на сервере и в CI: не из файла, а из переменных окружения, которые задаёт платформа — GitHub Actions Secrets, Docker --env-file, хранилища секретов.
  • Секрет в ноутбуке — та же утечка: вывод ячеек сохраняется в файл .ipynb. Не печатай ключи и не вставляй их строкой в код ячейки.
  • GitHub сам ищет секреты (secret scanning) и может заблокировать пуш с узнаваемым токеном — но надеяться на это нельзя.
Проверь себяЧем os.environ["X"] отличается от os.getenv("X")?

Первое бросает KeyError, если переменной нет — так проверяют обязательные секреты. Второе возвращает None или значение по умолчанию — для необязательных настроек.

Фиксация версий: == вместо >=

Через полгода pip install pandas поставит другую версию, и код, который работал, может сломаться или тихо выдать другие цифры. Точные версии в requirements — гарантия, что проект соберётся так же, как у тебя сегодня.

ЗаписьЧто поставитсяДля чего
pandasсамая новая на момент установкиникогда для проекта
pandas>=2.22.2 или любая новее, включая 3.xбиблиотеки, которые публикуешь сам
pandas~=2.2.32.2.3, 2.2.4… но не 2.3«только исправления ошибок»
pandas==2.2.3ровно 2.2.3приложение, проект, эксперимент — по умолчанию

Семантическое версионирование (SemVer): MAJOR.MINOR.PATCH. PATCH — исправления, MINOR — новые возможности без поломок, MAJOR — может сломать старый код (pandas 1 → 2 поменял поведение многих функций). Так обещают авторы, но не всегда соблюдают — поэтому и фиксируют точно.

Прямые и транзитивные зависимости. Ты ставишь scikit-learn, а он тянет numpy, scipy, joblib. Зафиксировать только свои пакеты мало: обновится numpy — и всё равно может сломаться. Поэтому есть два файла: короткий список того, что ты используешь, и полный «замок» (lock) со всеми версиями.

ИнструментСписок «что нужно»Lock «что именно стоит»
pip + pip-toolsrequirements.inpip-compile → requirements.txt с ==
uvpyproject.tomluv.lock
poetrypyproject.tomlpoetry.lock
просто pippip freeze > requirements.txt — всё установленное с ==, включая мусор; для учебного проекта сойдёт, если окружение чистое
Почему это ML-проблема особенно

Новая версия библиотеки может не упасть, а поменять результат: другой сид по умолчанию, другой порог, другая реализация метрики. Метрика из README перестанет воспроизводиться, и ты не поймёшь почему. Плюс версия Python: укажи её в README или .python-version, а в pyproject.toml — requires-python.

СобесЧем requirements.txt отличается от lock-файла и зачем оба?

Список зависимостей описывает намерение: какие пакеты нужны проекту, часто с допустимыми диапазонами. Lock фиксирует точный результат установки — все пакеты, включая транзитивные, с конкретными версиями (иногда и хешами). Список удобно править руками, lock гарантирует, что у коллеги, в CI и на сервере будет одно и то же окружение.

Git в команде

Один в репозитории ты можешь писать «fix» и «правки». В команде история коммитов — документация: по ней ищут, когда сломалось, и собирают список изменений к релизу.

Тема 6 из 13 · Инструменты

Conventional Commits: feat:, fix:, docs:

Сообщение коммита по шаблону тип(область): что сделано. Тип сразу говорит, что это: новая возможность, исправление, документация. Такую историю читают люди и разбирают инструменты.

Лаборатория · проверка сообщения коммита

ТипКогдаПример
featновая возможностьfeat(features): add weekly activity counts
fixисправление ошибкиfix(train): use val set for early stopping
docsтолько документацияdocs: add results table to README
refactorпеределка без изменения поведенияrefactor(data): split loader into functions
testтестыtest: check no student in both splits
chore, build, ciобслуживание, зависимости, CIbuild: pin pandas==2.2.3
perf, styleскорость, форматированиеperf: vectorize feature computation
  • Формат: тип в нижнем регистре, область в скобках по желанию, двоеточие и пробел, описание в повелительном наклонении («add», не «added»), без точки в конце, первая строка до ~72 символов. Пустая строка — и подробности в теле, если нужно.
  • ! или BREAKING CHANGE: в теле — изменение ломает обратную совместимость.
  • Атомарность важнее формата: один коммит — одна логическая правка. «feat: add loader and fix README and update deps» — это три коммита. git add -p позволяет добавить в коммит часть изменений файла.
  • Язык: в командах в России пишут и по-русски, и по-английски — следуй правилу репозитория. Для портфолио английский понятнее всем.

Разрешение merge-конфликтов

Шаги «увидел маркеры → выбрал → add → commit» — в уроке 1.3. Здесь — почему конфликт возникает вообще: git сравнивает три версии файла — общего предка и две ветки. Если обе ветки поменяли одно место по-разному, выбрать за тебя он не может.

Лаборатория · трёхстороннее слияние
База — общий предок

      
main — твоя ветка (ours)

      
feature — сливаемая (theirs)

    

    РЕЗУЛЬТАТ git merge feature
    

    

    

  

  
    
    
  • Строка изменилась только в одной ветке — git берёт изменённую версию сам. Поэтому большинство слияний проходит без вопросов.
    • 
    
  • Одна строка — по-разному в обеих — конфликт. Это не ошибка, а вопрос к человеку: какой смысл правильный.
    • 
    
  • Взять целиком одну сторону для файла: git checkout --ours файл или --theirs. При rebase «ours» и «theirs» меняются местами — это частая путаница.
    • 
    
  • Конфликты в .ipynb — ад: ноутбук это JSON с выводами ячеек. Помогают nbdime (сравнение и слияние ноутбуков) и привычка не коммитить выводы (nbstripout).
    • 
    
  • Как конфликтов избегать: маленькие ветки и частые слияния, git pull перед началом работы, не форматировать весь файл в одном коммите с правкой логики, договориться, кто правит общий конфиг.
    • 
  

  

    
СобесПочему возникает merge-конфликт и как вы его решаете?
      
Git делает трёхстороннее слияние: сравнивает общий предок с каждой из двух веток. Если одно и то же место изменено в обеих по-разному, он не знает, какой вариант верный, и ставит маркеры. Решение: открыть файл, понять смысл обеих правок (посмотреть git log по веткам или спросить автора), собрать правильный вариант, убрать маркеры, прогнать тесты, git add и git commit. Если что-то пошло не так — git merge --abort.

Просмотр файлов: cat, less, head, tail -f

  
Открыть CSV на гигабайт в Excel — подвиг на 10 минут. В терминале первые строки, размер и число строк видно за секунду, а лог обучения можно смотреть вживую.


ls -lh data/raw/                 # размеры файлов в человеческом виде (K, M, G)
du -sh data/                     # сколько занимает папка целиком
head -5 studentInfo.csv          # первые 5 строк — увидеть заголовок и формат
head -1 studentInfo.csv | tr ',' '\n' | cat -n   # столбцы с номерами — для cut
tail -3 studentInfo.csv          # последние строки: нет ли мусора в конце
wc -l studentInfo.csv            # число строк (минус заголовок — число записей)
less -S studentInfo.csv          # листать без переноса строк
column -s, -t < small.csv | less -S   # маленький CSV ровной таблицей
tail -f logs/train.log           # смотреть лог по мере записи; Ctrl+C — выйти

Пайпы и перенаправления: |, >, >>, 2>&1

  
У каждой программы три потока: ввод (0, stdin), вывод (1, stdout) и ошибки (2, stderr). Пайп соединяет вывод одной команды со входом другой, перенаправление отправляет поток в файл. Из маленьких команд собирается анализ данных в одну строку.

Ловушка с порядком
cmd 2>&1 > file отправит в файл только вывод, а ошибки — на экран: в момент 2>&1 поток 1 ещё смотрел на экран. Правильно — cmd > file 2>&1. Также logging в Python по умолчанию пишет в stderr — поэтому без 2>&1 логи не попадут в файл.

Права доступа: chmod, chown, sudo

  
У файла три группы пользователей — владелец, группа, все остальные — и три права для каждой: читать (r), писать (w), выполнять (x). Права записывают буквами rwxr-xr-x или тремя цифрами 755.


  

    
Лаборатория · калькулятор прав

    

      

      

        
755
chmod — число

        
-rwxr-xr-x
как в ls -l

      

    

    

    

  

  

    
Как считать число: r = 4, w = 2, x = 1, складываем для каждой группы. rwx = 7, r-x = 5, rw- = 6, r-- = 4. Три цифры — владелец, группа, остальные.

    
    
      
  • chmod +x run.sh — разрешить запуск (нужна ещё первая строка-шебанг #!/usr/bin/env python3 или #!/bin/bash), затем ./run.sh.
    • 
      
  • chmod 600 ~/.ssh/id_ed25519 — ключ SSH читает только владелец, иначе ssh откажется его использовать («permissions are too open»).
    • 
      
  • chown user:group файл — сменить владельца. Обычно нужно, когда файлы создал root (например, контейнер Docker).
    • 
      
  • sudo — выполнить от имени администратора. Не делай sudo pip install: сломаешь системный Python, ставь в venv. Не делай chmod 777 «чтобы заработало» — это дыра, ищи, кому на самом деле не хватает прав.
    • 
      
  • У папки «x» значит «можно зайти внутрь» (cd), «r» — «можно посмотреть список файлов».

Тема 11 из 13 · Инструменты

  
Переменные окружения, PATH, .zshrc

  
Переменная окружения — пара «имя=значение», которую процесс получает при запуске и передаёт своим детям. PATH — список папок, где терминал ищет программы. ~/.zshrc — файл, который zsh выполняет при открытии каждого нового терминала: там живут твои настройки.


echo $PATH | tr ':' '\n'          # папки поиска программ по порядку — выигрывает первая
which -a python3                  # все python3 в PATH: какой запустится и какие «спрятаны»
export DATA_DIR=~/data/oulad      # переменная для этого терминала и запущенных из него программ
DATA_DIR=/tmp python script.py    # только для одной команды
env | grep -i data                # посмотреть, что задано

# ~/.zshrc — постоянные настройки
export PATH="$HOME/.local/bin:$PATH"     # своя папка программ — в начало
alias ll="ls -lah"                       # короткая команда
alias venv="source .venv/bin/activate"

source ~/.zshrc                   # перечитать без перезапуска терминала

  
    
    
  • Наследование только вниз: программа видит переменные родителя, но изменить окружение родителя не может. Поэтому export в одном окне не виден в другом, а скрипт ./set_env.sh не меняет твой терминал — нужно source set_env.sh.
    • 
    
  • activate в venv — это и есть правка PATH: .venv/bin ставится в начало (урок 1.3). Поэтому после активации python — это Python из окружения.
    • 
    
  • .zshrc и .zprofile: .zprofile выполняется при входе в систему (один раз), .zshrc — для каждого интерактивного терминала. На macOS терминал по умолчанию zsh; на серверах часто bash — там ~/.bashrc.
    • 
    
  • Секреты в .zshrc — плохая идея: они видны всем программам и попадают в бэкапы. Лучше .env проекта (тема 4).
    • 
  

  

    
Проверь себяТы установил программу, а терминал пишет «command not found». Что проверишь?
      
Есть ли её папка в PATH (echo $PATH, which); если программа ставится в ~/.local/bin — добавить в PATH через .zshrc и сделать source ~/.zshrc; для Python-пакетов — активирован ли нужный venv.

Jupyter Notebook и Lab

  
Ноутбук — это код, разбитый на ячейки, плюс ядро (kernel) — живой процесс Python, который помнит всё, что ты выполнил, в том порядке, в котором выполнил, а не в том, как ячейки стоят на экране. Отсюда и сила ноутбуков, и их главная ловушка.


  

    
Лаборатория · скрытое состояние

    
Выполняй ячейки в любом порядке кнопками ▶. Потом нажми «Restart & Run All» — так ноутбук увидит коллега.

    

    

    

    

  

  
    
    
  • Номера [3] слева — порядок выполнения. Если они идут не по возрастанию сверху вниз — результаты на экране могли получиться из другого порядка.
    • 
    
  • Перед коммитом и перед тем, как показать — Kernel → Restart & Run All. Упало — значит, ноутбук держался на скрытом состоянии.
    • 
    
  • Магические команды: %timeit и %%time — замер скорости; %load_ext autoreload + %autoreload 2 — подхватывать правки в src/ без перезапуска ядра; %pip install — поставить пакет в окружение именно этого ядра.
    • 
    
  • Ядро = окружение: выбери ядро из .venv проекта (нужен ipykernel, урок 1.3). Чужое ядро — чужие версии библиотек.
    • 
    
  • Notebook или Lab: Lab — современный интерфейс с вкладками, файлами и терминалом в одном окне. В VS Code ноутбуки открываются прямо в редакторе, с отладчиком и подсказками кода — для проекта удобнее всего.
    • 
    
  • Ноутбуки в git: выводы ячеек раздувают файл и порождают конфликты. nbstripout убирает выводы при коммите; ноутбуки называют с номером и смыслом: 01_eda.ipynb, 02_baseline.ipynb.
    • 
  

  
Когда код уезжает из ноутбука в src/
Скопировал одну функцию во второй ноутбук — пора выносить в src/. Ноутбук после этого становится коротким: импорт, вызов, график, вывод текстом. Так EDA проекта А (неделя 3) и устроишь.

  

    
СобесКакие минусы у Jupyter-ноутбуков в продакшен-разработке?
      
Скрытое состояние и произвольный порядок выполнения — результаты трудно воспроизвести. Плохо тестируются и импортируются, плохо ревьюятся и конфликтуют в git из-за JSON с выводами, поощряют копипасту. Поэтому ноутбуки — для исследования и отчётов, а повторяемый код — в модулях с тестами; ноутбук перед показом всегда прогоняют Restart & Run All.
