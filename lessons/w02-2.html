Порядок в данных

Отсортировать — не только «расставить по возрастанию». Это выбор ключа, понимание цены (n log n), и инструмент: на отсортированных данных многие задачи решаются за один проход двумя указателями.

Тема 1 из 9 · Python

sorted с key=, lambda

Ключ (key) — функция, которая для каждого элемента говорит, по какому значению его сравнивать. Python вызывает её один раз на элемент, сортирует по результатам и сохраняет исходный порядок равных. Почти любую «хитрую» сортировку можно записать одним правильным ключом.

Что такое sort и sorted, reverse и кортеж из нескольких полей — в уроке 1.2. Здесь — как выбирать ключ и на чём ловят.

Ловушка с буквой «ё»

Сортировка строк идёт по кодам символов, а «ё» в Юникоде стоит после «я»: sorted(["ёж", "яблоко", "ель"]) → ['ель', 'яблоко', 'ёж']. Для русского текста — key=lambda s: s.lower().replace("ё", "е") или настоящая локаль через locale.strxfrm. Та же история с заглавными: «аня» с маленькой окажется после «Яна».

Где это в ML

Отсортировать модели по метрике, признаки по важности (sorted(zip(names, model.feature_importances_), key=itemgetter(1), reverse=True)), объекты по предсказанной вероятности для порога и PR-кривой. В pandas то же самое — df.sort_values(["group", "score"], ascending=[True, False]), и у него есть параметр key=, работающий со столбцом целиком.

СобесКак отсортировать список словарей по двум полям: группа по возрастанию, балл по убыванию?

sorted(rows, key=lambda r: (r["group"], -r["score"])): кортежи сравниваются слева направо, минус переворачивает порядок числа. Если оба поля текстовые, делают два стабильных прохода: сначала sort(key=второе, reverse=True), потом sort(key=первое) — стабильность сохранит порядок первого прохода внутри равных групп.

СобесСколько раз вызывается функция key при сортировке n элементов?

Ровно n раз: Python сначала вычисляет ключ для каждого элемента (декорирует), потом сортирует по готовым ключам. Поэтому тяжёлый ключ не умножается на n log n сравнений. С cmp-функцией наоборот: она вызывается на каждое сравнение.

Проверь себяЧто вернёт sorted(["10", "9", "100", "2"])? А с key=int?

['10', '100', '2', '9'] — строки сравниваются по первому символу. С key=int — ['2', '9', '10', '100'], и элементы остаются строками.

Merge sort и quick sort

Оба алгоритма работают по принципу «разделяй и властвуй». Merge sort делит массив пополам, сортирует половины и аккуратно сливает их — всегда O(n log n), стабильно, но нужна дополнительная память. Quick sort выбирает опорный элемент, раскидывает меньшие налево, большие направо и повторяет — в среднем быстрее всех, на месте, но в худшем случае O(n²).

Как устроены

# Merge sort: разделить, отсортировать половины, слить
def merge_sort(a):
    if len(a) <= 1:
        return a
    mid = len(a) // 2
    left, right = merge_sort(a[:mid]), merge_sort(a[mid:])
    out, i, j = [], 0, 0
    while i < len(left) and j < len(right):     # два указателя по двум отсортированным кускам
        if left[i] <= right[j]:                    # <= — равные берём слева: так сохраняется стабильность
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1
    return out + left[i:] + right[j:]

# Quick sort: опорный, разбиение, рекурсия (понятная версия, не на месте)
import random
def quick_sort(a):
    if len(a) <= 1:
        return a
    p = random.choice(a)
    return quick_sort([x for x in a if x < p]) + [x for x in a if x == p] + quick_sort([x for x in a if x > p])

Откуда log n. Merge sort делит массив пополам, пока куски не станут по одному элементу: это log₂n уровней (как в бинарном поиске из урока 1). На каждом уровне слияние проходит по всем n элементам. Итого n · log n. У quick sort то же самое, если опорный элемент делит кусок примерно пополам. Если опорный каждый раз оказывается самым маленьким, уровней не log n, а n — отсюда n².

Как спасают quick sort: случайный опорный элемент, «медиана из трёх» (первый, средний, последний), а в библиотеках — introsort: начинают quick sort, а если рекурсия ушла слишком глубоко, переключаются на heap sort.

Что внутри Python. sorted и list.sort — это Timsort: гибрид merge sort и сортировки вставками. Он находит уже упорядоченные куски («раны») и сливает их, поэтому на почти отсортированных данных работает почти за O(n), всегда стабилен и в худшем случае O(n log n). np.sort по умолчанию — quicksort-подобный (introsort), не стабилен; нужна стабильность — kind="stable".

Нижняя граница. Любая сортировка, которая только сравнивает элементы, в худшем случае делает не меньше порядка n log n сравнений. Быстрее можно, только если пользоваться значениями: сортировка подсчётом за O(n + k) для небольших целых чисел (оценки 2–5, возраст).

Где это в ML и на собеседованиях

Писать сортировку руками на работе не придётся, а на алгоритмической секции — бывает: «реализуйте merge sort», «слейте два отсортированных массива» (это кусок merge sort), «найдите k-й по величине элемент» — quickselect, тот же partition из quick sort, но рекурсия только в одну сторону, O(n) в среднем (LeetCode 215).

СобесЧем merge sort отличается от quick sort и почему в Python не quick sort?

Merge sort всегда O(n log n), стабилен, но требует O(n) дополнительной памяти. Quick sort в среднем быстрее и сортирует на месте, но в худшем случае O(n²) и не стабилен. Python использует Timsort — гибрид merge sort и вставок: он стабилен (это важно для сортировки по нескольким ключам в несколько проходов), гарантирует O(n log n) и очень быстр на реальных данных, где часто есть уже упорядоченные куски.

СобесЧто значит «стабильная сортировка» и когда это важно?

Стабильная сортировка сохраняет исходный порядок элементов с равными ключами. Важно, когда сортируют по нескольким признакам в несколько проходов, и когда исходный порядок что-то значит — например, время поступления заявок с одинаковым приоритетом.

Проверь себяПочему quick sort с последним опорным элементом на уже отсортированном массиве делает n²/2 сравнений?

Последний элемент — максимум куска, все остальные уходят влево. Каждый вызов отщепляет всего один элемент, и уровней рекурсии получается n, а не log n: (n−1) + (n−2) + … ≈ n²/2. В лаборатории: 120 сравнений для 16 элементов.

Два указателя

Два индекса идут по массиву, и на каждом шаге по простому правилу двигается один из них. Вместо перебора всех пар за O(n²) — один проход за O(n) и O(1) памяти. Работает, когда у данных есть порядок: массив отсортирован, или ответ зависит от концов.

Лаборатория · указатели шагают

Почему это правильно, а не везение

Two Sum II, массив отсортирован. Сумма крайних меньше target? Тогда левый элемент не подойдёт ни с одним правым: справа от правого указателя никого не осталось, а все остальные ещё меньше. Его можно выбросить — сдвигаем левый. Сумма больше — по той же логике выбрасываем правый. Каждый шаг отбрасывает целую строку возможных пар, поэтому шагов не больше n.

Container With Most Water: площадь ограничивает более низкая стенка. Если сдвинуть высокую, ширина уменьшится, а высота не вырастет — хуже быть не может только с низкой. Поэтому двигаем низкую стенку.

# Шаблон «навстречу» — Two Sum II
def two_sum_sorted(a, target):
    l, r = 0, len(a) - 1
    while l < r:
        s = a[l] + a[r]
        if s == target:
            return l, r
        if s < target:
            l += 1          # a[l] слишком мал для любого партнёра
        else:
            r -= 1          # a[r] слишком велик для любого партнёра
    return None

# Шаблон «быстрый и медленный» — Move Zeroes на месте
def move_zeroes(a):
    slow = 0
    for fast in range(len(a)):
        if a[fast] != 0:
            a[slow], a[fast] = a[fast], a[slow]
            slow += 1
Два указателя или хеш-таблица

Two Sum из урока 1.3 на неотсортированном массиве — словарь: O(n) времени и O(n) памяти. Если массив уже отсортирован — два указателя: O(n) времени и O(1) памяти. Сортировать специально ради указателей — это O(n log n) и потеря исходных индексов. На собеседовании назови оба варианта и выбери по условию.

СобесКак решить 3Sum (тройки с суммой 0) быстрее, чем O(n³)?

Отсортировать массив за O(n log n). Для каждого i запустить два указателя на отрезке справа от i и искать пары с суммой −a[i]. Это O(n²) всего. Дубликаты пропускать: если a[i] равен предыдущему — следующий i, и после найденной тройки сдвигать указатели мимо одинаковых значений.

2 + 15 = 17 < 18 → l вправо. 7 + 15 = 22 > 18 → r влево. 7 + 11 = 18 — индексы 1 и 2.

Код, который не падает молча

Ошибки будут всегда: битая строка в CSV, нет файла, сеть отвалилась посреди запроса к API. Хороший код не тот, где ошибок нет, а тот, где понятно, что случилось, ресурсы закрыты, а данные не потеряны.

Тема 4 из 9 · Python

try / except / else / finally

try — код, который может упасть. except — что делать, если упал с конкретной ошибкой. else — что делать, если не упал. finally — что выполнить в любом случае: была ошибка или нет, поймали её или нет.

Лаборатория · какие строки выполнятся
Вывод и результат

Зелёный фон — строка выполнилась, красный — здесь возникла ошибка, бледные строки пропущены.

Иерархия ошибок: что ловить

Исключения — это классы, и они наследуются друг от друга. except LookupError поймает и KeyError, и IndexError. Верх иерархии: BaseException → Exception → всё, что обычно ловят. KeyboardInterrupt (Ctrl+C) и SystemExit лежат вне Exception — именно поэтому except Exception не мешает остановить программу, а голый except: мешает.

  • Лови узко. except ValueError, а не except Exception: так ты обрабатываешь ожидаемую ситуацию, а опечатку в имени переменной (NameError) увидишь сразу.
  • Голый except: и except: pass — никогда. Это «проглотить всё молча»: код вроде работает, а половина данных потерялась.
  • Несколько типов: except (ValueError, TypeError) as e:. Порядок блоков — от частного к общему.
  • Свои исключения: class DataError(Exception): pass — понятное имя для ошибки твоей предметной области.
  • Пробросить дальше: raise без аргументов внутри except — та же ошибка с исходным traceback. raise DataError("битый CSV") from e — новая ошибка с указанием причины.
class DataError(Exception):
    """Данные не прошли проверку."""

def read_scores(path):
    try:
        f = open(path, encoding="utf-8")
    except FileNotFoundError as e:

    else:

            return [int(x) for x in f]

Ловушка: return в finally

return внутри finally перекрывает и результат из try, и даже вылетевшее исключение — оно молча исчезнет. В finally только освобождают ресурсы и пишут логи, ничего не возвращают.

Где это в ML

Чтение грязных данных: плохую строку пропускаем, но считаем и логируем, сколько пропущено, — иначе модель тихо учится на половине датасета. Запросы к API (LLM, загрузка датасета): ловим сетевые ошибки и повторяем с паузой, растущей вдвое (exponential backoff). Долгое обучение: KeyboardInterrupt ловят, чтобы сохранить чекпоинт перед выходом. А assert — для проверок своего кода, не для данных пользователя: при запуске с python -O они выключаются.

СобесЗачем нужен else в try, если можно написать код в конце try?

Чтобы except ловил ошибки только из той строки, которую мы действительно ожидаем упасть. Код в else выполняется, если try прошёл без ошибок, и его исключения уже не попадут в наш except — не замаскируются под «ожидаемую» ошибку.

СобесПочему except: без типа — плохая практика?

Он ловит всё, включая KeyboardInterrupt, SystemExit и ошибки в собственном коде (NameError из-за опечатки). Программа перестаёт останавливаться по Ctrl+C, а баги прячутся. Ловить нужно конкретные ожидаемые исключения; если уж широко — except Exception с логированием и обычно повторным raise.

Проверь себяВ лаборатории выбери row = {}. Почему finally выполнился, а return — нет?

KeyError не подходит под except ValueError, поэтому не пойман. finally выполняется всегда, даже при непойманной ошибке, а потом исключение летит дальше, к вызывающему коду, и до return дело не доходит.

Тема 5 из 9 · Python

Контекстные менеджеры и with

with гарантирует, что после блока ресурс будет освобождён: файл закрыт, блокировка снята, соединение отпущено — даже если внутри блока вылетела ошибка. По сути это готовый try / finally, упакованный в объект.

# вручную
f = open("log.txt", "w", encoding="utf-8")
try:
    f.write("старт\n")
finally:
    f.close()

# то же самое через with
with open("log.txt", "w", encoding="utf-8") as f:
    f.write("старт\n")
# здесь файл уже закрыт, даже если write упал

Как это устроено. Объект в with — контекстный менеджер: у него есть методы __enter__ (вызывается в начале, его результат попадает в as) и __exit__(exc_type, exc, tb) (вызывается в конце, получает ошибку, если она была). Если __exit__ вернёт True, ошибка считается обработанной и подавляется — так работает contextlib.suppress.

Свой менеджер за пять строк — через декоратор contextmanager: всё до yield — вход, после — выход.

import time
from contextlib import contextmanager, suppress

@contextmanager
def timer(name):
    start = time.perf_counter()
    try:
        yield                                  # здесь выполняется тело with
    finally:
        log.info("%s: %.2f с", name, time.perf_counter() - start)

with timer("обучение"):
    model.fit(X_train, y_train)

with suppress(FileNotFoundError):              # «удали, если есть» — без try/except
    Path("cache.pkl").unlink()

with open("in.csv", encoding="utf-8") as src, open("out.csv", "w", encoding="utf-8") as dst:
    ...                                         # несколько ресурсов в одном with

СобесЧто такое контекстный менеджер и как написать свой?

Объект, который управляет ресурсом в блоке with: __enter__ получает ресурс, __exit__ освобождает его в любом случае, даже при исключении. Свой пишут классом с этими двумя методами или функцией-генератором с декоратором @contextlib.contextmanager: код до yield — вход, после — выход, обычно в try/finally. Примеры: таймер, временная смена настроек, транзакция БД.

Проверь себяЧто будет с файлом, если внутри with open(...) as f: вылетит ValueError?

Файл закроется (сработает __exit__), а ValueError полетит дальше: open ошибки не подавляет.

logging вместо print

print пишет всё одинаково и только в консоль. logging пишет с уровнем важности, временем и источником, умеет одновременно в консоль и в файл, а лишнее отключается одной настройкой, без удаления строк из кода.

Консоль

Код вызывает одни и те же семь строк логов. Уровень обработчика решает, что из них попадёт в его вывод. Двигай ползунки.

import logging
log = logging.getLogger(__name__)                 # свой логгер в каждом модуле

def main():
    logging.basicConfig(                          # настройка один раз — в точке входа, не в библиотечном коде
        level=logging.INFO,
        format="%(asctime)s | %(levelname)s | %(name)s | %(message)s",
        handlers=[logging.StreamHandler(), logging.FileHandler("train.log", encoding="utf-8")],
    )
    log.info("Загружено %d строк из %s", len(df), path)   # %-подстановка: строка соберётся, только если уровень включён
    try:

    except OSError:

  • Логгер (getLogger(__name__)) — кто пишет. Обработчик (handler) — куда: консоль, файл, сеть. Формат — как выглядит строка. У логгера и у каждого обработчика свой уровень.
  • log.exception внутри except — сообщение уровня ERROR плюс traceback. Это вместо print(e), который теряет, где именно упало.
  • Не f-строки в логах: log.debug("loss=%s", loss), а не log.debug(f"loss={loss}") — f-строка соберётся, даже когда DEBUG выключен.
  • Ротация: RotatingFileHandler(maxBytes=…, backupCount=…), чтобы лог долгого обучения не съел диск.
Где это в ML

Скрипт обучения на сервере идёт часами, а ты закрыл ноутбук. Утром открываешь train.log и видишь, сколько строк пропущено, какая была ошибка на валидации на каждой эпохе и где упало. С print всего этого просто нет. Для метрик экспериментов есть отдельные инструменты (MLflow, Weights & Biases — неделя MLOps), но базовый лог нужен всегда.

СобесПочему logging лучше print?

Уровни важности: подробности отключаются настройкой, а не удалением кода. Время, модуль и уровень в каждой строке. Несколько выводов сразу — консоль и файл, у каждого свой уровень. log.exception сохраняет traceback. Библиотеки пишут в свои логгеры, и приложение решает, что из этого показывать.

copy и deepcopy

Что такое поверхностная и глубокая копия и почему b = a — не копия, разобрано в уроке 1.2 с лабораторией памяти. Здесь — где копии решают на практике: конфиги из JSON, таблицы pandas, массивы numpy и лучшая модель во время обучения.

Конфиг по умолчанию и настройки эксперимента

DEFAULTS = {"model": {"depth": 6, "lr": 0.05}, "features": ["attendance", "gpa"]}

def make_config(overrides):
    cfg = DEFAULTS.copy()                  # поверхностная: внутренний словарь "model" — тот же объект
    cfg["model"]["lr"] = overrides["lr"]   # испортили DEFAULTS для всех следующих экспериментов
    return cfg

def make_config(overrides):
    cfg = copy.deepcopy(DEFAULTS)          # правильно: вложенные словари и списки тоже новые
    cfg["model"].update(overrides)
    return cfg

Это классический баг серии экспериментов: второй запуск неожиданно получает параметры первого, потому что «дефолты» молча поменялись. Признак — результат зависит от порядка запусков.

Ответ
  • Изменяемое значение по умолчанию cfg={}: один словарь на все вызовы, копит «n» из прошлых запусков. cfg=None и внутри cfg = {} if cfg is None else cfg.

  • Относительный путь по умолчанию: зависит от папки запуска. Путь от Path(__file__) или аргументом.
  • Голый except: pass: глотает и KeyError из-за опечатки в заголовке, и всё остальное, а пропущенные строки не посчитаны. except ValueError + счётчик + log.warning с номером строки.

        for n, r in enumerate(csv.DictReader(f), start=2):   # 1-я строка — заголовок
            try:
                r["score"] = int(r["score"])
            except ValueError:
                bad += 1
                log.warning("строка %d: плохой балл %r", n, r["score"])
                continue
            rows.append(r)
    log.info("загружено %d, пропущено %d", len(rows), bad)
    return sorted(rows, key=lambda r: (r["group"], -r["score"]))

«Merge sort или quick sort? И что использует Python?»

Готово, когда назвал сложность в среднем и в худшем случае, память, стабильность и Timsort.

Каким должен быть ответ

Оба O(n log n) в среднем. Merge sort гарантирует O(n log n), стабилен, но O(n) доп. памяти. Quick sort в среднем быстрее, на месте, но O(n²) при плохом опорном (лечится случайным опорным или медианой из трёх) и не стабилен. В Python — Timsort: гибрид слияния и вставок, стабилен, O(n log n) в худшем случае и почти O(n) на почти отсортированных данных. Плюс к ответу: для top-k — heapq.nlargest, для k-й статистики — quickselect за O(n) в среднем.

«Зачем with, если можно вызвать close()?»

Готово, когда объяснил исключения, __enter__/__exit__ и привёл пример своего менеджера.

Каким должен быть ответ

Если между открытием и close() вылетит исключение, до close() дело не дойдёт — файл, соединение или блокировка останутся висеть. with вызывает __exit__ в любом случае — это try/finally, спрятанный в объект. Свой менеджер — класс с __enter__ и __exit__ или @contextmanager с yield, например таймер этапа обучения или временная смена настроек.
